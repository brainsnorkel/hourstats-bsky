# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

HourStats is a Go-based Bluesky bot that monitors the firehose in real time via Jetstream, performs VADER sentiment analysis on English posts, and publishes 30-minute summaries with the top 3 most engaged posts, sparkline charts, trending topics, and yearly sentiment visualizations.

**Live bot:** [@hourstats.bsky.social](https://bsky.app/profile/hourstats.bsky.social)

## Key Commands

### Build and Run
```bash
go run ./cmd/hourstats                  # Run locally (set env vars first)
make build-hourstats                    # Build binary (CGO_ENABLED=0)
make deploy-prod                        # Deploy to Fly.io production
make deploy-staging                     # Deploy to Fly.io staging
make deploy-all                         # Deploy both
```

### Testing and Development
```bash
make test                               # Run all tests (go test ./...)
make fmt                                # Format code (go fmt ./...)
make lint                               # Lint (requires golangci-lint)
make deps                               # go mod download && go mod tidy
make graph-lab                          # Generate chart experiments (no API needed)
```

### Operations
```bash
make fly-status                         # Check both app statuses
make fly-logs-prod                      # Tail production logs
make fly-logs-staging                   # Tail staging logs

fly ssh console -a hourstats-prod       # SSH into production
fly ssh console -a hourstats-prod -C "su-exec hourstats realign -dry-run"   # One-off sentiment realignment (see below)
```

## Architecture

### Single Binary, Multiple Goroutines

Everything runs inside `cmd/hourstats/main.go` on Fly.io:

| Component | Trigger | What It Does |
|-----------|---------|-------------|
| **Jetstream Consumer** | Always running | WebSocket firehose, filter English posts, write to SQLite |
| **Write Flusher** | 2s ticker / 1500 batch | Batches pending writes to reduce SQLite contention |
| **Analysis Cycle** | Wall-clock ticker (default 30m, configurable; prod runs 60m at :55 via `ANALYSIS_INTERVAL_MINUTES`/`ANALYSIS_OFFSET_MINUTES`) | Hydrate engagement, score sentiment, post summary. Sentiment covers the window minus the posts hydration attempted and lost; posts its deadline never reached (batches go oldest first) are scored, since firehose deletes already reach `post_buffer` live, while the top posts are ranked among the hydrated posts only. One `window population` line logs `window_posts`, `hydrated`, `never_attempted`, `attempted_lost` and `attempted_lost_pct`. The window is scored twice: the headline (net percent, category, root/reply split) comes from the emoji-aware analyzer (`analyzer.NewEmojiAware`) since 2026-09-11, and stock VADER (`analyzer.New`) scores the same window into `net_sentiment_pct_stock`; the `sentiment scorers` log line reports both and their delta. The summary's "Bluesky is #<word>" hashtag is one of 22 mood words in seven percentile tiers (`internal/formatter/sentiment_100_words.go`), cut from 100 on 2026-09-28 so each word spans more than the typical hour-to-hour move (retired list in docs/MOOD_WORDS_RETIRED_2026-09-28.md). Runs in its own goroutine so the other tickers keep firing; an overlapping tick is skipped and logged as `cycle_overlap_skipped`. A memory sampler runs alongside it (500ms, `cmd/hourstats/memsampler.go`), writing a `cycle_memory_tick` event at each of its 20 timeline checkpoints (1s to 3000s) and a `cycle_memory_peak` event at the end, so a cycle killed by the OOM killer still leaves a trace; the memory guard (`cmd/hourstats/memguard.go`) rides on the same samples. The cycle's heavy work — the window read, hydration and the topic goroutine — runs on a child context the guard can cancel, while the run/sentiment/purge writes stay on the parent so a trip still records the hour |
| **Sparkline** | After analysis | 7-day sentiment chart posted as reply |
| **Trending Topics** | After sparkline | TF-IDF + grouping (Gemini primary → `GROUP_FALLBACK_MODEL` → suppress, all inside `GROUPING_TOTAL_TIMEOUT_SECONDS`; a suppressed hour gets no trending reply and no footer topic, and the offline co-occurrence clustering is only tried when `TOPICS_OFFLINE_FALLBACK=true`), reply to sparkline (if enabled). The grouping prompt opens with today's UTC date and asks for no year a term does not carry; after keyword normalisation (and on the offline path) a label naming a year before `topics.LabelYearFloor` that no keyword carries has the year stripped, and the cluster is dropped only when the label is then unusable (fails validation, ends on a function word, under 3 letters), logged as one `topics: label year rule` line with `label_year_stripped` and `label_year_dropped`; the footer blanks a stored past-year label from rows written before that rule. Analysis starts when hydration returns, because its corpus joins `topic_tokens` to `post_buffer` on non-zero engagement and only hydration writes engagement (started earlier, as before hs-aqa.2, it described the previous hour); it overlaps scoring, the feature gate and the summary post, and its `topics: loaded tokens for TF-IDF` line carries `created_at_min`, `created_at_median` and `created_at_max` so the corpus's hour can be read off the log. The cycle collects its result (bounded 90s wait: the summary posts ~4.5 s after hydration, grouping takes ~5 s typically and 55 s at worst) before the single seven-day `sentiment_history` read that opens the posting block, so this cycle's rank-1 label is already on its `top_topic` row when that read happens. Those same points feed both the chart and the trending reply's footer. The trending reply is posted after the sparkline and ends with a three-line footer: a `7day high & low UTC` header, then one line per extreme of the form `+14.1% Mon 14:01: <rank-1 label>` (the label and its colon are omitted when unknown; no calendar date, no link). The footer is the first thing dropped when the post would exceed 300 graphemes: its topic labels shrink from 28 to 12 runes, then go, then the whole footer, all before any topic is dropped. After that, trailing topics are dropped whole rather than listed without their exemplar link; only the rank-1 topic gives up its link before its label is cut. It is also dropped when the sparkline failed and the trending post goes out standalone, since the figures only read as a caption on the chart above them |
| **Daily Cycle** | Midnight UTC | SQLite backup to S3, daily aggregation (now including the day's firehose total), report rollups (`topic_daily` for the last 3 days, `daily_top_post` for every day `runs` still covers, firehose backfill for daily rows that predate the column), top-post quote reply. Runs in its own goroutine, after waiting up to max(15m, `HYDRATION_TIMEOUT_MINUTES` + 5m) for an in-flight analysis cycle so the aggregate includes the day's last cycle |
| **Weekly Report** | End of the daily cycle (`REPORTS_ENABLED`) | Week-in-review text root (mood, delta vs prior week, happiest/unhappiest day, top topic, posts analysed) plus a reply quoting the post of the week. Covers the last complete Monday–Sunday week; the guard key `weekly_report_last_week` makes it a no-op until a new week exists, so it posts on Monday and catches up if that run was skipped; the key is armed at process start when `REPORTS_ENABLED` is first set (and by this job if still absent), so a stale week never goes out. The top topic line (`Top topic: <label>, #1 for N of 168 hours`) counts exact rank-1 cycles from `sentiment_history.top_topic` (`GetTopRankOneSubjectForRange`), grouped by `topics.SubjectKey` (lowercased, years and `us`/`the`/`a`/`of`/`in`/`on` dropped, a plural `s` folded), so the grouper's hour-to-hour spellings of one subject count together; the winner has the most cycles (ties to the later last cycle, then the key), its most frequent exact label is shown, and N is cycles × the interval, capped at 168. `topic_daily` is no longer read by the weekly: it counts ranks 1-5 under fragmented IDs or exact labels and overstated sticky runners-up such as Halloween. A label naming a 19xx/20xx year before the week's first year costs the post its topic line, with no fallback to another spelling or the runner-up subject (the runner-up of a mislabelled election week is another election) (`weeklyReport.droppedTopicYears`, which calls `topics.PastLabelYears`, the year regexp the grouper's label year rule shares; the rule is unchanged: the grouper was date-blind and has labelled the 2026 midterms a 2024 election, and its slips run backwards, so later years such as a post-midterm "2028 Presidential Race" are kept; a season, fiscal or full range like `2025-26`, `2024/25` or `2025-2026` is judged by its end year, while a two-digit tail more than thirty years on, or a four-digit one running backwards, is not a range, so `2024-11-05` is judged as 2024; in January the year just ended is kept too, so a `2026 Year in Review` in the first week of 2027 keeps its line; `$2000` and `Election2024` are not years (defence in depth: the grouper's label allowlist admits no currency sign), a bare `Over 2000 Flights` is; a label genuinely about an earlier year loses the line too). Logged as a Warn `weekly report: topic label names a year before the week, topic line dropped` with the label and the years, carried as `topic_dropped_years` on the `DRY_RUN` and `weekly report posted` lines, and, once the post has gone out, written as a `weekly_report_topic_dropped` stats event that the alert path raises as a warning, so a drop the Sunday preview could not foresee still reaches Discord. The post-of-the-week reply prints the live like/repost/reply counts and handle from the feature gate's `getPosts` view (`counts_source=live` on its log line), falling back per field to the stored hour-one figures when the view has none. Skipped with fewer than 5 daily rows. Known quirk: when Sunday's top post is also the week's, the daily quote reply and this reply embed the same post a minute apart. **Sunday preview** (`cmd/hourstats/weekly_preview.go`): at the end of the Sunday daily job (~00:35–00:50 UTC on prod, after the cycle wait and the VACUUM) the coming week's root text is built from the six days then available and posted to the Discord webhook as `HourStats <profile> weekly report preview · week <range> · posts Monday 00:00 UTC`, with a ⚠️ status line when the week is short, the topic line is missing or cut, or it was dropped for a year before the week (the dropped label is shown as inline code in the flag, since the text no longer carries it), and in that case the exact `fly ssh console … sqlite3 -cmd '.timeout 5000' … INSERT OR REPLACE INTO key_value … weekly_report_last_week` command that skips the week; Sunday's own rows land in Monday's job, so the topic and post of the week can still change. Logged as `weekly report preview` (`week_start`, `ok`, `days`, `topic`, `flags`, `discord`, `text`); an unset webhook means log only; a failed post writes a `weekly_report_preview_failed` stats event, which the alert path re-raises as a warning at the next snapshot. No preview on a Sunday means the week is unreviewed (the daily job was skipped or interrupted); `REPORTS_RUN_AT_STARTUP=preview` is the manual fallback |
| **Monthly Report** | After yearly posting (`REPORTS_ENABLED`) | Candlestick chart root plus a volume chart reply (English and, when tracked for every day, the full firehose; when every day also has a language split, the firehose is stacked as English plus the top 5 languages plus "other"). Covers the previous calendar month; guard key `monthly_report_last_month` (posts on the 1st, catches up if skipped, including on first enable). Skipped with fewer than 20 daily rows. The chart header's "vs <month>" delta is the same mean-daily figure the text prints (`volumeDelta`, passed in as `MonthlyVolumeMeta.PrevDeltaPct`), the share tile divides by the firehose totals rather than the language stack, and busiest/quietest are chosen among full days only (`sparkline.VolumeExtremes`: days with the month's maximum cycle count), with a footnote on the chart and a clause in the alt text when partial days were excluded, so an hour lost to an OOM kill cannot be named the quietest day |
| **Yearly Posting** | 1st of month 01:00 UTC | 365-day sentiment chart, pinned to profile. Same goroutine/guard as the daily cycle, so chart rendering never overlaps a cycle or a daily run; a skipped tick logs `job_overlap_skipped`. Its `<Mon> <D> events` link facets point at the per-day `Portal:Current_events/YYYY_Month_D` subpage (built by `internal/wikipedia`) rather than an anchor into the monthly page; it is the only post that links to Wikipedia |
| **Stall Detection** | 5m ticker | Warns if no posts received in 5m and force-closes the WebSocket so the consumer reconnects. The `stall_detected` event carries the consumer's connection state and last dial error: `last_post_age`, `connected`, `forced_reconnect`, `reconnects_since_last_check`, `endpoint` (host only), `protocol`, `last_error` (quoted, `"none"` when there is none, at most 200 runes, URL query strings stripped) and `last_error_age`. `forced_reconnect=false` with `connected=false` means the consumer was already reconnecting (in its dial/backoff loop), not that the detector failed |
| **WAL Checkpoint** | 5m ticker | Pressure-based WAL checkpoint: PASSIVE under threshold, TRUNCATE over threshold (default 50MB) |

Wall-clock aligned scheduling: tickers fire at UTC clock boundaries so deploys don't shift the schedule. An optional offset (`ANALYSIS_OFFSET_MINUTES`) shifts the fire point within each interval.

### Data Flow

```
Bluesky Jetstream -> Consumer (filter English) -> SQLite post_buffer
                                                       |
30-min ticker -> Read posts -> Hydrate engagement (25 URIs/batch, 10 concurrent)
                                    |
                            VADER sentiment (window minus attempted-and-lost)
                                    -> Top 3 by engagement (hydrated only) -> Post summary
                                    |
                            Sparkline reply -> Trending topics reply
                            (trending reply ends with "7day high & low UTC" and one "+14.1% Mon 14:01: label" line per extreme)
```

Every surface that features an individual user's post passes one feature gate
(`internal/client/gate.go`, `(*BlueskyClient).NewFeatureGate`): the hourly
summary, the trending exemplars, and the daily and weekly quote replies. One
authenticated `app.bsky.feed.getPosts` (up to 25 URIs; viewer state is only
populated when authenticated) plus one `VisibilityResolver` lookup per distinct
author DID (4 at a time) yields a `Verdict{OK, Quotable, Reason, AuthorDID}` per
URI. `OK=false` means no quote, no link, no handle, with `Reason` one of
`missing` (absent from the authenticated view: deleted, taken down,
deactivated), `blocked` (`Viewer.BlockedBy`/`Blocking`/`BlockingByList`, either
direction), `adult_label`, `label:<val>` (any `!`-prefixed moderation label on
the post or the author, covering `!hide`, `!warn`, `!no-unauthenticated`,
`!takedown`), `hide_from_recommendations` (the author's content visibility
declaration) or `visibility_unknown` (the declaration could not be read twice
running — a user we cannot check is not featured). `quote_control`
(`Viewer.EmbeddingDisabled`) leaves `OK=true` with `Quotable=false`: the post is
still listed with its handle link, but the record embed is dropped and the
summary's first line gains `· no embed, post can't be quoted`. Each URI gets one
`feature_gate` log line (`surface`, `uri`, `ok`, `quotable`, `reason`). The
hourly cycle gates 10 ranked candidates and lists the first 3 that pass, before
the run row is written, so `daily_top_post` and the weekly report inherit the
decision; exemplars are gated before their text is sent to Gemini. Unlike the
old quote-control check, the gate fails closed: after one retry, an unreachable
gate costs the hourly summary its top posts entirely — it is posted with no top
posts at all, just the aggregate sentiment lines, and the run row records none
either so the daily and weekly reports cannot inherit one — drops every
exemplar for the cycle, and skips the daily and weekly replies (their guard keys
are still set).

### SQLite Database

Single file on Fly.io persistent volume: `/data/hourstats-{profile}.db` (WAL mode).

Three connection pools: `writeDB` (1 conn, 30s timeout), `readDB` (4 conns, read-only), `maintDB` (1 conn, 1s timeout for WAL checkpoints).

Key tables: `post_buffer` (2h retention), `runs` (48h), `sentiment_history` (nominally 8 days, but the purge has no caller so every hourly cycle since Jan 2026 is retained), `daily_sentiment` (3 years), `topic_tokens` (26h), `topic_snapshots` (48h), `topic_daily` and `daily_top_post` (400 days, rolled up from `topic_snapshots` and `runs` by the daily cycle), `language_counts` (per cycle, 8 days) and `language_daily` (400 days), `key_value` (permanent). Post counts on `runs` and `sentiment_history`: `total_posts` (`total_posts_retrieved` on `runs`) is the analysed population, the window minus posts hydration attempted and lost; `window_posts` is the whole window read and `hydrated_posts` what hydration reached (both 0 on rows before 2026-11-04, except the three silent US-election-night rows `run-20261104-025500`, `-035500` and `-045500`, backfilled by hand from their `hydration_timeout` events; bead hs-thk.5 decided on 2026-11-04 to leave those rows in the series rather than exclude them: they score the oldest 89%, 75% and 66% of their windows, 145-148k posts each, and their net percentages sit between their neighbours'). On an hour where hydration completes `total_posts` equals `hydrated_posts`; before hs-thk.4 it always did, so truncated election-night hours from before that change undercount. The volume reports (`GetDayCycleTotals`, the daily `total_posts` rollup and the monthly volume chart) sum `total_posts`. `sentiment_history` carries both scorers: `net_sentiment_percent` is the headline, which since 2026-09-11 is the emoji-aware score (`analyzer.NewEmojiAware`) and is mirrored into `net_sentiment_pct_emoji` for continuity with the shadow era, while `net_sentiment_pct_stock` holds the same window scored by stock VADER (`analyzer.New`), the pre-switch headline. Both are NULL for rows written before their column existed and for cycles where that scorer failed; a NULL `net_sentiment_pct_stock` is exactly what marks a row as pre-switch, which is how `cmd/realign` finds the rows to move. `cmd/realign` (shipped as `/usr/local/bin/realign`) is the one-off tool that put the pre-switch history on the new scale. Run it as the app user — `fly ssh console -a hourstats-prod -C "su-exec hourstats realign -dry-run"` — because an ssh session is root and every file it writes as root is a file the uid-1000 bot cannot then write; the entrypoint repairs that on the next boot (`find /data -maxdepth 2 ! -user hourstats -exec chown ... +`), but not before it. Its flags: `-dry-run` (default) reports the shift S against `formatter.RealignShift` and prints samples, `-apply` rewrites history inside one `BEGIN IMMEDIATE` transaction after a local backup, `-revert` restores the originals from the `sentiment_history_prealign` and `daily_sentiment_prealign` snapshot tables (both are in the essential-tables backup while they exist). It records `sentiment_realign_shift`, `sentiment_realign_applied_at`, `sentiment_realign_row_count`, `sentiment_realign_max_timestamp` and `sentiment_realign_shadow_rows` in `key_value`; `sentiment_scorer_v2_since` (the first UTC day on the new scorer) is written by the bot itself at startup, like `firehose_count_v2_since`. See docs/SENTIMENT_REALIGNMENT_PLAN.md.

Firehose transport: the consumer speaks Jetstream v2 by default (`wss://jetstream.us-{west,east}.bsky.network/xrpc/network.bsky.jetstream.subscribeEvents`, subprotocol `xrpc.v1.json`, `collections=app.bsky.feed.post`, `kinds=commit,account`, dictionary zstd; `internal/jetstream/v2.go` and `v2_session.go`). It resumes by unix-microsecond timestamp, rewound `JETSTREAM_CURSOR_REWIND_SECONDS` (5s by default), on every dial (an endpoint rotation is the exception: it follows repeated instability, so the new endpoint is dialled at its live tip): a cursor at or above 1e15 is read as a timestamp and translated to the first seq that instance witnessed at or after that instant, while a seq belongs only to the instance that issued it (two connections to the same hostname at the same moment read seqs 43 million apart). The witnessed time is persisted every 10s as `key_value` `jetstream_v2_cursor_time_us`, with the seq alongside it in `jetstream_v2_cursor` for diagnostics only, never read back for a resume. The seq still dedups within a single connection, with the floor reset at every dial; the replayed overlap is absorbed by the idempotent post upsert. Each dial logs `jetstream v2 dial` with `cursor_kind` (`timestamp` or `live`), `cursor_time` and `rewind`. The first v2 deploy finds no v2 cursor and starts from the live tip. Both protocols normalise frames into the same `jetstream.Event`, so the callbacks are protocol-agnostic: `OnPost` for creates, `OnDelete` for post delete commits (the row and its topic tokens are removed in order inside the write batch, and an in-memory tombstone with 15-minute retention stops a replayed create from resurrecting it), `OnAccountInactive` for `deactivated`/`deleted`/`suspended`/`takendown` accounts (every buffered post by that DID is purged; `desynchronized` and `throttled` are not purges). The counts are on the stats snapshot as `post_deletes`, `account_purges` and `tombstone_hits`. v2 also delivers repo backfill through the live tail as ordinary creates with fresh seq numbers and a current witness time but a record `createdAt` days to years old, which v1 never did, so a create lagging its witness time by more than `JETSTREAM_MAX_POST_AGE_MINUTES` is dropped at ingest — before `OnPost` and before `OnEarlyReject`, so it inflates neither the buffer nor the firehose and per-language totals — and counted as `stale_posts`.

Alerts: after each 30-minute stats snapshot, `internal/alerts` evaluates the two most recent snapshots, the `stats_events` rows since the older of them, and the live consumer report against the `ALERT_*` thresholds, and sends every condition down one notification path. The conditions are `dropped_posts` (error, only when the write buffer dropped posts in two consecutive snapshots), the three clamp counters `capped_posts`, `stale_posts` and `denied_posts` (info above their thresholds, and a warning only when the volume is large next to live traffic: capped at a quarter or more of the English posts stored, stale or denied above three times the firehose total), `oversized_posts` (over 100), `consumer_reconnects`, `cycle_duration`, `rss_high`, and one condition per alerting `stats_events` type in the window: `cycle_failed` (error; written when the cycle exits before its run row, i.e. the window read or the Bluesky login failed — the login is retried once after 10s),  `memory_guard_trip` (error), `memory_guard_warn`, `window_capped`, `hydration_ceiling_projected` (warn, not actionable; written at cycle start when the window exceeds the hydration ceiling, carrying `window_posts`, `ceiling_posts` and `projected_unhydrated_pct`, so the operator hears about a coming hydration timeout ~25 minutes early), `hydration_timeout`, `posting_skipped` (warn; written whenever the cycle publishes nothing, carrying `reason` — `memory_guard`, `window_capped`, `low_post_count` or `hydration_shortfall`, in that precedence — plus `window_posts`, `hydrated`, `never_attempted`, `attempted_lost_pct`, `ceiling_posts` and `rate_limited`; actionable only for `hydration_shortfall`, and for `low_post_count` when no `stall_detected` is in the same window, since the other reasons already page through their own event; a snapshot with `analysis_ran=1` and `posting_skipped=1` but no such event raises the same condition as a fallback, which `DRY_RUN` never sets), `consumer_restart`, `feature_gate_unavailable` (written by the analysis cycle when the gate is unreachable and the hour publishes no top posts at all), `grouping_failed` (warn, not actionable; written when every Gemini grouping tier failed and the hour has no trending reply, carrying the per-attempt `tier=model:class:elapsed` list), `weekly_report_preview_failed` (warn; the Sunday weekly preview could not be posted to Discord, so the coming week is unreviewed unless `REPORTS_RUN_AT_STARTUP=preview` is run), `weekly_report_topic_dropped` (warn, not actionable; Monday's weekly report went out without its stickiest-topic line because the label named a year before the week, carrying `week_start`, `years` and the `label`), `stall_detected` (error, actionable; written every 5 minutes while no posts arrive, with the consumer's connection state and last dial error — `connected=false` with reconnects means Jetstream is unreachable) and `seq_floor_reset` (written by `cmd/hourstats`'s `OnSeqFloorReset` callback when the v2 dedup floor has rejected 10,000 frames in a row and is reset to the live tip, carrying `dropped`, `floor` and `seq`). Every condition is logged as `alert` with its name, severity and message; info stays in the log and on `/stats/health`, while warn and error also go to `ALERT_DISCORD_WEBHOOK_URL` when it is set, at most once per condition name per hour. Messages are one line of fact (count, previous half hour, threshold, the live figure it is compared with) and one of meaning and what to check; the flood conditions (`stale_posts`, `capped_posts`, `denied_posts`) also name the top five accounts with counts and per-minute rates, with handles resolved for Discord and the top account's profile URL in angle brackets so Discord does not unfurl it, since the channel is the operator's own record (DIDs never appear at Info in the process log). `ALERT_DISCORD_MENTION` (e.g. `@here`) is prefixed only to actionable conditions and errors: `dropped_posts`, `memory_guard_trip`, `window_capped`, `consumer_restart`, `stall_detected`, `rss_high`, `cycle_duration`, `oversized_posts`, `consumer_reconnects`, `posting_skipped` (`hydration_shortfall` / `low_post_count` only). Because evaluation follows the snapshot, a page about an hour's cycle lands up to ~35 minutes after that cycle started. The evaluation runs off the scheduler loop on a 30s budget, and its result is what `/stats/health`'s `status` (`ok`/`warn`/`error`) and `alerts` array report.

Firehose counting: the Jetstream consumer drops non-English post creates with a bytes-level pre-filter before parsing. Since the language-volume change those frames still count toward the firehose total and toward `language_counts` (via `OnEarlyReject`); before it, "firehose" meant English plus untagged posts only, so `total_firehose_posts` values from before that deploy are undercounts. A post is counted as `en` when the English filter accepts it, otherwise under its first tag's primary subtag, with `und` for untagged.

## Coding Conventions

### Logging
- **Use `log/slog`** with structured key-value pairs: `slog.Info("message", "key", value)`
- JSON handler configured in main.go: `slog.NewJSONHandler(os.Stdout, ...)`
- Do NOT use `log.Printf` -- the codebase is migrating away from it

### Error Handling
- Wrap errors with context: `fmt.Errorf("failed to X: %w", err)`
- Log and return early on error -- no deep nesting
- Use `context.WithTimeout` for all external API calls

### Bluesky API Patterns
- Posts limited to 300 graphemes (use `[]rune` for length checks, not `len(string)`)
- Rich text facets use byte offsets (not rune offsets) for `ByteStart`/`ByteEnd`
- AT URIs: `at://did:plc:xxx/app.bsky.feed.post/yyy`
- Image upload: blob reference then embed in post record. `UploadImage` decodes the PNG header and sets the embed's `aspectRatio`; without it clients draw the image in a square frame with blank bands. The sparkline and yearly charts render at 2000×1333 (`sparkline.PostCanvasWidth/Height`), the CDN's full-size cap; feed thumbnails are served at 1000px wide regardless

### Testing
- Standard `go test ./...`
- `make report-rehearsal DB=<backup.db> [NOW=2026-11-09T00:30:00Z] [OUT=dir] [CYCLE_MINUTES=60]` builds the weekly and monthly report posts from a copy of a prod backup (`s3://hourstats-sqlite-backups/prod/`, essential tables including `topic_daily`, `daily_top_post` and `language_daily`) and prints every text and alt text with its rune count, writing the two charts to `OUT`. It is `TestReportRehearsal` in `cmd/hourstats`, skipped unless `HS_REPORT_REHEARSAL_DB` is set, and asserts nothing: it exists so a report change is read against real data before it is posted. No network; the post-of-the-week preview uses the stored counts
- Hydrator uses interfaces (`PostFetcher`, `PostUpdater`) for testability
- No external test framework -- stdlib `testing` package only

Each of those waits up to 30 min for the :55 cycle and then runs; the daily job does the backup, aggregation, rollups, quote reply, Sunday VACUUM and weekly report, and a restart there is cancelled with a 1 s budget while the daily aggregation has no catch-up (bead hs-12y), so the day's `daily_sentiment` row would be lost. In practice: after `analysis cycle complete` and before :45 of any hour except 00 and 01 UTC

## Important Notes

- Bluesky post limit is 300 **graphemes** (runes), not bytes
- Facet byte positions must be calculated on the UTF-8 byte string
- The Jetstream consumer auto-restarts with exponential backoff (1s to 60s)
- Cursor is persisted in SQLite for resume-on-restart: v2 in `key_value` (`jetstream_v2_cursor`), v1 in the `cursor` table
- `DRY_RUN=true` prevents all posting but still runs analysis and stores data
- The AWS Lambda/DynamoDB code is gone from the repo (git history only); the only AWS dependency left is the daily S3 backup in `internal/store/backup.go`
