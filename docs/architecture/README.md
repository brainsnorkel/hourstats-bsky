# HourStats architecture

Diagrams of the Fly.io single-binary HourStats bot as it is at the time of writing (September 2026). Every fact on them was read from the code, not from older documents; where the code and the older prose disagreed, the code won and the disagreement is listed under "Review notes" below.

Two toolchains are used on purpose:

- **Mermaid** (`*.mmd`, rendered to `svg/`) for the views that are mostly lists and sequences, where a text source that diffs well matters more than pixel-perfect placement.
- **Excalidraw** (`excalidraw/*.excalidraw`, generated by `excalidraw/build.py`, exported to `svg/ex-*.svg`) for the three boxes-and-lines views where hand layout beats auto-layout: context, static components, deployment. Open the `.excalidraw` files in excalidraw.com or the VS Code Excalidraw extension to edit; rerun the script to regenerate from scratch.

"Re-normalising processes" (view 7) is read as: the processes that pull the system back to normal after something goes wrong or drifts. They are grouped by where they act: firehose ingest (reconnect, backoff, endpoint rotation, stall detection, cursor rewind and age cut-off, write-buffer backpressure), storage housekeeping (WAL checkpointing, the Sunday VACUUM, retention purges, boot-time maintenance), the analysis cycle (overlap guards, hydration retries and the `low_confidence` gate, the Gemini fallback chain, the bounded topic wait, the 300-grapheme trimming order, the quote-control check), catch-up and idempotence (three-day rollup window, guard keys, backfills), and the shutdown sequence that keeps a rolling deploy from losing buffered posts.

## Regenerating

```sh
# Mermaid → svg/ and png/ (png is gitignored, used for visual review)
npm install -g @mermaid-js/mermaid-cli
sh docs/architecture/render.sh

# Excalidraw sources
python3 docs/architecture/excalidraw/build.py
```

`mermaid-config.json` pins the neutral theme and a Helvetica/Arial font stack; the per-file `%%{init}%%` directives only carry layout spacing. The Excalidraw SVGs were exported with `@excalidraw/utils` in headless Chrome; any Excalidraw export will do.

## Review notes

Each diagram was rendered and inspected, then the set was checked against the code. What follows is what the review turned up, so a reader knows where the pictures simplify and where the system itself is surprising.

### Per view

- **Context.** The bot has seven outside dependencies, not the three the README leads with. Google News RSS is called on every grouping (three feeds, 3 s timeout, silently skipped on failure) and Wikipedia is link-only. Hydration deliberately goes to the public AppView, not the PDS, to keep the per-IP rate budget on bsky.social free for posting; `HYDRATION_HOST=pds` reverses that.
- **Static components.** Mermaid's auto-layout could not draw this without crossings; the Excalidraw version is the one to read. Package-level imports were split into view 2b so the component view only shows which goroutine drives which package. `internal/store` is the only shared leaf; `internal/topics` reaches Bluesky solely through an injected `TrendingPoster` interface, which is why it is not drawn calling the PDS directly.
- **Static data.** Retention is enforced by explicit purge calls, and only for some tables. `runs`, `sentiment_history` and `daily_sentiment` have purge functions with no production caller, and the `ttl` columns are never read; the diagram says "never purged" where that is the case rather than repeating the nominal 48 h / 8 day figures from CLAUDE.md. `token_postings` is rebuilt at boot and not maintained on the ingest path.
- **Ingest sequence.** The bytes-level language pre-filter runs before JSON parsing and only inspects the first 256 bytes after `"langs":`; anything it cannot classify is kept and re-checked after parsing. Rejected frames still count toward the firehose and language totals.
- **Analysis cycle sequence.** Topic analysis and hydration overlap; the summary is posted before the cycle waits (at most 60 s) for the topic result, so the sparkline reply and the trending reply are what the wait protects. The emoji-aware shadow score is computed and stored on every cycle but never influences anything posted. Purges run on the early-exit paths as well as the publish path.
- **Daily and yearly sequence.** The yearly chart is posted every day at 01:00 UTC with no "already posted this month" guard; only the minimum-seven-days check gates it. The daily quote depends on `yearly_post_uri`/`yearly_post_cid` existing in `key_value`. Both the weekly and monthly reports run nightly and rely on guard keys to be no-ops.
- **Re-normalising processes.** Two mechanisms are close to invisible in logs and worth knowing: the Gemini daily budget is a rolling 24 h window from process start, not a calendar day, and the write flusher's shutdown drain has a 4 s budget inside the 5 s the shutdown sequence allows it, so a machine that is SIGKILLed after 15 s always had its cursor persisted first.
- **Deployment.** Both apps run with `--ha=false` (one machine each). The stats API on port 9111 is not exposed by `fly.toml`; it is reachable only through `fly proxy` or from inside the machine. Local backups are pruned by `BACKUP_RETAIN_DAYS` (7 in the production config); S3 has no lifecycle rule in code.

### The whole

- The set is complete for the running binary: every goroutine in `cmd/hourstats/main.go`, every table in `internal/store/store.go`, and every outbound host appear at least once.
- The diagrams intentionally omit `cmd/graph-lab` and `cmd/hourstats-stats` from everything except the package graph; they are developer tools, not part of the deployed system.
- Numbers on the diagrams (batch sizes, timeouts, thresholds) are the defaults in code unless labelled "prod", in which case they come from `fly.prod.toml`.
- The older `docs/SEQUENCE_DIAGRAMS.md` described the AWS Lambda pipeline and has been removed; nothing in it applied to the Fly.io binary.
